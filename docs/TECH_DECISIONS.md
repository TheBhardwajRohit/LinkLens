# Tech decisions

Every stack choice, and the reason for it. This file is the answer to "why this stack?".

## The short answer

LinkLens has four jobs, and each part of the stack was picked for one of them.

| Job | What was picked | The one-line reason |
|---|---|---|
| Open a dangerous link without getting hurt | Playwright + Chromium in its own Docker container, behind our own filtering proxy | A real browser sees what a victim would see (redirects, scripts, the final page), and the container plus proxy make sure a hostile page can't reach anything private. |
| Work out who is behind it and how risky it is | Python + FastAPI, with NetworkX, TLSH, imagehash, and a LightGBM model run in plain Python | The analysis libraries that matter (fuzzy hashes, graphs, DNS, registries, machine learning) are Python libraries. FastAPI runs many lookups at once and streams progress. |
| Remember every page it has seen | PostgreSQL (local in Docker, Supabase when online) | Fingerprints, families, and saved scans are relational data with a few indexed searches. One ordinary database does all of it; no vector database, queue, or cache server was needed. |
| Show the result to anyone, for free | A static React site on GitHub Pages, data jobs on GitHub Actions | Static files cost nothing to host and can't be hacked into running code. Actions gives a fresh, isolated machine for every run, which is the safe place to visit scam pages. |

Three ideas run through all of it:

1. **Safety decides the shape.** The API never touches a target link; only the sandbox does, and it has no secrets. That one rule is why there are separate containers, a proxy, and three separate jobs for feed ingestion.
2. **Everything must be explainable.** Every point of the score is a sentence a person can read. Even the model's opinion arrives with the features that pushed it. That is why rules came first and the model was added on top, not the other way round. And the model is never trusted alone: it was checked on real pages from outside its dataset, found to be wrong about small honest sites, and limited (rows 64 and 71 to 73).
3. **Free has to mean free.** Every service was checked against its real limits before it was used, and the app keeps working when a key is missing or a quota runs out. Things that would have needed money or a risky workaround were dropped (see the table at the end).

| 30 | TLS certificate capture | In the sandbox, through a separate connection checked by the SSRF guard | Reading the certificate means contacting the site, which only the sandbox may do. | 31 | Scoring (v1) | Hand-written rules, each a plain-words reason with points; good signs subtract | Every point on the score can be explained to a person, which matters more than a slightly better number at this stage. | 32 | Brand list | Hand-made JSON of 60+ brands scammers copy (global and Indian), with official domains and search words | Small, reviewable, and easy to extend. | 33 | Popularity signal | Tranco top 100,000, refreshed monthly | A research ranking built to resist manipulation. Free-hosting platforms are ranked as a whole, so their individual sites are judged separately. | Alexa (discontinued), Cisco Umbrella list alone | Decided |
| 34 | Saving scans | Postgres with plain SQL (psycopg), one `scans` table with a JSON column | One table and three queries don't need an ORM or migration tool yet. | 35 | Live progress | In-memory jobs streamed as Server-Sent Events; polling as the fallback | One-way updates are all the page needs, and SSE works over plain HTTP with built-in browser support. Jobs are kept 15 minutes, so a slow page can still catch up. No queue or Redis needed yet. | WebSockets, Redis pub/sub | Decided |
| 36 | Privacy of saved scans | Emails, tokens, and session IDs removed from every stored link; shared links always show the cleaned copy | Links often carry personal data (reset tokens, emails). Only the person who ran the scan sees the link exactly as pasted, in their own live stream. | Storing links as pasted | Decided |
| 37 | Blacklist sources | Google Safe Browsing (key set), Phishing.Database lists checked locally, urlscan.io search (no key needed). VirusTotal and URLhaus are built and switch on when a free key is added. | Each source answers a different question: Google covers phishing and malware at scale, Phishing.Database is a big free list we can check without sending anything out, urlscan.io shows whether others have looked at the site. Every source always ends with a plain status, so a missing key or a used-up quota never breaks a scan. | Paid feeds; PhishTank (sign-ups closed) | Decided |
| 38 | Blacklist timing | The pasted link is checked first, before the sandbox opens it; the final page and the stops in between are checked again during recon | Gives a first answer in about 2 seconds. Scam links often hide behind shorteners, so the real destination needs its own check. Links already checked come from the cache. | One check at the end | Decided |
| 39 | Lookup cache | Memory first, plus a `lookup_cache` table in Postgres | VirusTotal allows 500 free checks a day and 4 a minute, so answers must survive restarts. Google's "listed" answers are kept exactly as long as Google says (its `cacheDuration`). | Memory only (lost on restart); Redis (one more service) | Decided |
| 40 | Phishing lists in memory | A sorted array of 8-byte hashes, searched with binary search | About 450,000 entries cost under 4 MB this way; a plain Python set of strings would need around 60 MB. A false match would need two entries to share a 64-bit hash, which is practically impossible at this size. | Python set of strings; loading the lists into Postgres (500 MB limit on the free plan) | Decided |
| 41 | What leaves the server during a check | Links with emails, tokens, and session IDs removed; only the site name goes to urlscan.io; private-address stops are never sent | Safety rule 7. Lookups still match, because blacklists list the host and path, not someone's personal token. | Sending links as pasted | Decided |
| 42 | Google's key in a header | `x-goog-api-key` header, not `?key=` in the address | HTTP libraries log request addresses. A key in the address could end up in a log file. | Key in the query string (Google's examples) | Decided |
| 43 | Page fingerprints | TLSH of the HTML, an exact hash and a 64-bit similarity hash (simhash) of the tag sequence, a simhash of the visible words, pHash of the screenshot, MurmurHash3 of the favicon | Each one survives a different kind of change. TLSH tolerates edited code, the tag hashes ignore the words, the word hash ignores the layout, pHash catches pages that only look alike, and the favicon catches kits that keep their icon. A match needs at least two of them to agree. | ssdeep (left out: the pure-Python build is slow, and TLSH gives a graded distance); TF-IDF vectors stored per page (too big for a 500 MB database, so the 40 most used words are kept instead) | Decided |
| 44 | Finding similar pages fast | Each 64-bit hash is cut into four 16-bit pieces stored in one `bands` array with a GIN index | Two hashes that differ in three bits or fewer always share a piece, so one indexed query finds the candidates and only those are compared in full. No special database extension is needed. | Comparing against every stored page (too slow); a vector database (one more service) | Decided |
| 45 | Favicon capture | The sandbox loads the icon in a second tab of the same browser | That way the icon request goes through the same filtering proxy and SSRF guard as the page. Only its bytes are hashed; it is never opened as an image or shown. | Fetching it from the API (breaks safety rule 1); Playwright's request API (may skip the proxy for local names) | Decided |
| 46 | What is stored per page | Fingerprints, a few facts for finding siblings (IP, network, registrar, name servers, certificate names), the page's most used words, the sites it links to, and a 240 px thumbnail | Roughly 1 kB a page plus a few kB of thumbnail, so a few hundred thousand pages fit in the free database. Raw HTML is never stored. Feed thumbnails are dropped after 30 days. | Storing HTML or full screenshots (size, and it would mean hosting scam pages) | Decided |
| 47 | Dataset loading | PhreshPhish streamed from Hugging Face, read in windows of 256 rows by a pool of worker processes | The 36 GB dataset never touches the disk. One pass produces both the fingerprints (for families) and the feature file (for the model). Runs in Docker or on Actions, never straight on Windows, where the antivirus may quarantine phishing HTML. | Downloading the dataset first | Decided |
| 48 | Feed ingestion on Actions | Three jobs: plan (may read the database), visit (no secrets, `permissions: {}`), store (database and MaxMind key) | The job that opens live scam pages has nothing worth stealing. It fingerprints the pages itself, so raw HTML never becomes a GitHub artifact; only fingerprints and a thumbnail are passed on. | One job with everything (a misbehaving page could reach the database secret) | Decided |
| 49 | Schedule switch | The hourly schedule is skipped unless the repository variable `INGEST_ENABLED` is `true` | Without a shared database there is nowhere to store pages, and hourly runs that throw their work away would waste GitHub's free minutes. | Always running | Decided |
| 50 | No keep-alive | Dropped the planned "keep-alive" for scheduled workflows | GitHub pauses schedules after 60 days without repository activity. The best-known keep-alive action was taken down by GitHub staff for breaking the terms of service, so working around the pause is not allowed. If it ever happens, GitHub sends an email and one click (or `gh workflow enable`) turns the schedule back on. | A keep-alive commit or API call (against GitHub's terms) | Decided |
| 51 | Features for the model | 82 numbers read from the link and the page only; popularity rank and "this is the brand's real site" are left out | Research datasets hold a link and its HTML, nothing about who registered the domain. And because the benign half is mostly popular sites, a model given popularity would only learn "unpopular means scam". The rules still use popularity as a good sign. | Feeding the model everything | Decided |
| 52 | What counts as "the same design" | Points for each kind of fingerprint that agrees (code, structure, wording, look, icon); a match needs 3 points from at least 2 kinds, and one of them must be about content (wording, look, or icon) | Site builders such as Wix or Google Sites give thousands of unrelated pages the same code and structure, so those two alone prove nothing. One lucky match (the same default icon, the same tiny error page) must never link two pages. Requiring two independent kinds to agree keeps false links rare, and the same rule is used by the nightly grouping and by live scans. | A single threshold on one hash | Decided |
| 53 | Grouping into families | Connected components over those links, with candidates found through shared hash pieces. In big buckets each page is compared with a few neighbours and anchors, not with everyone. | On 55,000 pages this takes about 12 seconds, and the dataset's own brand labels show the groups are clean (see PROGRESS.md), so the heavier Leiden or HDBSCAN step is not needed yet. Groups that are mostly ordinary pages (a blog theme, a parked-domain page) are skipped as common templates. | Leiden or HDBSCAN from the start (more to tune, no clear gain at this size) | Decided, revisit when families start to chain |
| 54 | Family numbers | A family's number is the id of its oldest page | The number then stays the same from one night to the next, so "Family #12" in a saved report still means the same family later. | Renumbering every night | Decided |
| 55 | Sibling sources | Our own page library, the certificate (names on it and on its history), registration details, urlscan.io's public history for the IP address, and DNS for lookalike names | All public records, and none of them visits a site. Networks where one address serves thousands of sites (Cloudflare, Fastly, Akamai, GitHub Pages) are named as such and earn no points. | A paid reverse-IP service | Decided |
| 56 | Lookalike names | Up to 90 small variations of the name (another ending, a dropped or doubled letter, swapped neighbours, look-alike characters, an added hyphen or digit), each looked up in DNS | Shows which neighbours of a name really exist, in about two seconds, without opening any of them. The report says plainly that existing does not mean scam. | dnstwist (a whole extra tool for the few rules we need) | Decided |
| 57 | Link graph | SiNMULI's Algorithm 2 on the scanned site's neighbourhood only: edges signed by the site they start at, the balance rule for unknown signs in triangles, then the 51% vote over incoming links | Follows the paper (read on arXiv, 2608.19190v1) and stays fast because only a few dozen sites are involved. It abstains when links are few or disagree, which is the honest answer for most new domains. | Running it over the whole library on every scan (slow, and no better for one site) | Decided |
| 58 | Graph library | NetworkX in the API | Small graphs, so plain Python is fast enough, and it has PageRank, eigenvector centrality, and clustering built in. | igraph (faster, but one more compiled library in the scan server) | Decided |
| 59 | Network map | Cytoscape.js, loaded only when a report has links to draw; names appear on hover or click, with the same content as a plain list underneath | Canvas drawing copes with dozens of nodes, drag and zoom come built in, and the list keeps it usable without a mouse or with a screen reader. The page's security policy allows exactly one inline style by its hash: the one-line rule Cytoscape adds. | D3 force layout (more code), drawing our own | Decided |
| 60 | Server map | Leaflet with OpenStreetMap tiles, loaded only after the visitor clicks "Show on a map" | The tiles come from OpenStreetMap's servers, the only third party the site ever talks to, so the visitor chooses. OpenStreetMap's tile rules are followed: their exact tile address, visible credit, no bulk loading. A dot is drawn instead of Leaflet's pin image. | Always showing the map (a third-party request on every report); a static world image (no zoom) | Decided |
| 61 | The model | Gradient-boosted trees (LightGBM), trained on PhreshPhish feature numbers | The standard choice for table-like features: strong results with little tuning, fast to train (seconds), and each tree is a readable set of questions. The numbers are in `docs/MODEL_REPORT.md`. | A neural network on the raw HTML (needs far more data and a GPU, and can't explain itself); logistic regression (misses how signals combine) | Decided |
| 62 | Running the model | The trees are saved as plain JSON and walked by about 40 lines of Python in the API | The scan server needs no LightGBM and none of its system libraries, so the image stays small for a free host. The training job checks that the plain walker gives the same answers as LightGBM, and fails if not. | Loading LightGBM in the API | Decided |
| 63 | Explaining the model | For each prediction, the change in a tree's expected answer at every question is credited to the feature asked about (the Saabas method) | Simple, exact (the credits add up to the model's output), and needs nothing beyond the trees. The report then says "mostly because of ..." in plain words. | SHAP values (the better-known method, but it needs LightGBM or the shap library at scan time) | Decided |
| 64 | Rules and model together | The model's opinion is one more reason with points (up to +50, down to -20), but it counts in full only when the rules alone already scored 8 or more. Alone it adds at most 20 and never lifts a page out of Safe | On the dataset the model is strong (it catches 75.9% of unseen scam pages, and 97.5% of what it flags is a scam). But the dataset's honest pages are mostly large pages of popular sites, so the model takes a small honest page for a scam page. Of 126 real honest pages it rates 13 as likely scams. Above Safe in a scan with the limits: 1. Without them: 5. The price, measured on the dataset: rules plus model mark 41.2% of scam pages Suspicious or worse instead of 63.1%. A live scan has domain age, certificates, blacklists, and families to back the model up; a dataset has none of those. | The model's probability as the score (not explainable, and wrong for small honest sites); the model always counting in full (the first version, which flagged small honest sites); rules only (weak on unseen kits) | Decided |
| 65 | Where the model file lives | `api/app/ml/model.json` (about 300 kB) is committed to the repo | The API must work right after `git clone` and `docker compose up`, with no download step. It is small, changes only when retrained, and is derived data, not a dataset. | A release download at startup (one more thing that can fail) | Decided |
| 66 | PDF report | A print layout of the report page; the browser's print window saves it as a PDF | The plan suggested rendering the page with Playwright, but the only Playwright we have is the sandbox, which must never load internal pages. Printing from the visitor's own browser needs no server work, handles every script (Hindi titles included), and keeps the sandbox rule intact. | A second browser container just for PDFs; a PDF library on the server (needs fonts for every script) | Decided |
| 67 | Bulk scans | Up to 10 links per request, run one after another | The sandbox opens one page at a time on purpose (memory, and it keeps volume modest). A small list is enough for one person checking a batch of messages. | Parallel sandboxes (more memory than a free host has) | Decided |
| 68 | API keys | Random keys shown once, stored only as SHA-256 hashes; each key has its own hourly limit | A leaked database can't leak the keys. Keys are for scripts; the website never needs one. | Storing keys in plain text; a full user-accounts system (far more than a personal project needs) | Decided |
| 69 | Rate limits behind a host | The caller's address is read from `X-Forwarded-For` only when `TRUST_FORWARDED_FOR` is on | Behind a cloud host every request seems to come from the host's proxy, which would give all visitors one shared limit. Reading the header blindly would let anyone fake their address, so it is opt-in. | Always trusting the header | Decided |
| 70 | Free host for the scan server | Azure Container Apps, with the Azure for Students offer (guide in `docs/DEPLOY.md`, not yet deployed) | It runs our two containers unchanged, scales to zero so it costs nothing while idle, and has a free grant every month (180,000 vCPU-seconds, 360,000 GiB-seconds, 2 million requests). No credit card is needed for students. | Render free (512 MB, too small for Chromium), Hugging Face Docker Spaces (now paid), Oracle free VMs and Google Cloud Run (both need a card), GitHub Actions (its terms forbid serving an app) | Decided, waiting for the account |
| 71 | What the model is not shown | The query string, the whole link's length, whether the site is on free hosting, popularity, and "this is the brand's real site" | Each would teach a shortcut that is true of the dataset and false on the web. The dataset has next to no honest links with a query string (1 of 21,715) or on free hosting (65 of 21,715). Given the query string, the first model called all 63 of 63 real honest pages likely scams once a newsletter tag was added to their links. A later version that still saw the free-hosting flag rated 8 of 17 real honest pages on github.io and similar services as likely scams. Its honest pages are also mostly popular sites, so popularity would teach "unpopular means scam". The rules still use all of these, in the open. | Keeping them and weighting the data (weights can't help where there are no honest examples to weight) | Decided |
| 72 | Weighting the training data | Honest pages count for more (up to 20 times) in groups, by page size and bare address, where scam pages outnumber them | In the dataset a small page or a bare site address is nearly always a scam; on the web most are honest. Weighting makes those two facts say nothing on their own, without throwing data away. Measured with everything else the same: honest test pages under 100 tags wrongly flagged fell from 22.2% to 8.1%, and real honest pages rated likely scams fell from 28 to 13. | Dropping the page-size numbers (lost more accuracy and fixed less); weighting both ways (more false alarms on large pages); made-up small pages (invented data) | Decided |
| 73 | Checking the model outside the dataset | `jobs/honest_check.py`: 126 well-known honest pages, scanned through the local scan server; training reports on them every time | A test split drawn from the same dataset shares its blind spots. This short list is how the shortcuts in rows 71 and 72, and the rule problems in rows 77 to 79, were found. It is a sanity check, not a clean test, and the report says so. | Trusting the test split alone | Decided |
| 74 | Tests and the trained model | API tests run on the rules alone; only tests marked `real_model` load the shipped model | A verdict in a test should not change because the model was retrained. One marked test fails if the model and the feature list drift apart, which would otherwise quietly switch the model off. | Every test running the real model (four tests broke the first time it shipped) | Decided |
| 75 | Blacklisted links and good signs | An exact listing on a trusted list makes the verdict at least Likely dangerous; a weaker listing is never Safe | With points alone, good signs (an old domain, a calm model) could pull a listed link down to Safe. A listing is the one thing treated as confirmed, so it sets a floor. | Bigger points for listings (still beatable by enough good signs) | Decided |

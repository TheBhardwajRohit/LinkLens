# Tech decisions

Every stack choice, and the reason for it. At the end of the project, this file is the answer to "why this stack?".

**Status:** *Decided* = agreed with Rohit (2026-09-24).

| # | Area | Choice | Why | Alternatives considered | Status |
|---|---|---|---|---|---|
| 1 | Website hosting | GitHub Pages | Free, lives in the same repo, and Rohit wanted GitHub. Static files only, which fits because our backend is separate. | Vercel, Netlify (also free, but another account) | Decided |
| 2 | Scheduled jobs | GitHub Actions | Free and in the repo (public repo, so no minute limit on standard runners). Each run gets a fresh throwaway VM, which is a safe, isolated place to visit scam pages (safety rule 10). GitHub's terms make data-collecting cron a gray area; Rohit accepted that risk. | Cron on a VM, Celery beat | Decided |
| 3 | Database + screenshots | Supabase (free plan) | A real Postgres database (what the plan needs), plus file storage for screenshots and a read-only API the static website can use. All in one free account. | Neon (Postgres only, no file storage); JSON files in the git repo (size limits, every save is a commit, parallel jobs clash) | Decided, account not created yet |
| 4 | Live scan server | Docker containers, on Rohit's PC for now | GitHub can't run a server, and Actions' terms forbid using it as part of a serverless app. Containers move to any host unchanged, so the host can be picked later. | Free cloud hosts, to compare in phase 10 | Decided for now; host still open |
| 5 | Website framework | Vite + React + TypeScript | The site is a static single-page app talking to a separate API. Next.js's main extras (server rendering, API routes) don't work on GitHub Pages, so Vite gives the same React ecosystem with less setup. | Next.js static export (works, but most of its features go unused); Astro | Decided |
| 6 | Styling and motion | Tailwind CSS, Motion (the new name of Framer Motion) | Fast to build a consistent dark theme; smooth card animations, scroll effects, and tilt, with built-in reduced-motion support. | Plain CSS, GSAP | Decided |
| 7 | 3D hero graph | react-three-fiber (Three.js), glossy instanced spheres and "rails", studio-light reflections | The standard way to do WebGL in React. Instanced meshes draw every node and link in two draw calls, so it stays fast. The graph shows real scan data, not decoration. | Plain Three.js; CSS dots (the first idea, but we'd have thrown it away) | Decided |
| 8 | Maps and graphs | Cytoscape.js (network map), Leaflet + OpenStreetMap (server map) | Both free, no API keys, and built for exactly these jobs. | D3 force graph, Mapbox (needs a key) | Decided |
| 9 | API | Python + FastAPI | Python has the analysis libraries we need (TLSH, pHash, DNS, graphs, ML). FastAPI handles many lookups at once (async), checks inputs, and supports live progress. | Node + Express (weaker analysis libraries), Django (heavier) | Decided |
| 10 | Sandbox browser | Playwright + Chromium, own container | Records redirects, every network request, and screenshots. Well maintained, with a Python API. | Puppeteer (Node only), Selenium (less network detail) | Decided |
| 11 | Job queue | None at first (no Celery, no Redis) | Scheduled work runs on Actions. The scan server has one user and low volume, so FastAPI background tasks are enough. Fewer containers also make free hosting easier. Add arq or RQ with Redis if scans start piling up. | Celery + Redis (from the original brief) | Decided |
| 12 | Live progress | Server-Sent Events | One-way updates from server to browser. Simpler than WebSockets, and works over plain HTTP. | WebSockets, polling | Decided |
| 13 | Local dev database | Postgres in Docker | Tests run offline, without touching shared data or free quotas. It's the same Postgres Supabase uses. | Supabase CLI local stack (many containers) | Decided |
| 14 | Icons | lucide-react | Clean, consistent line icons; only the ones we use end up in the bundle. | Hand-drawn SVGs, Heroicons | Decided |
| 15 | Fonts | Red Hat Display (headings), Red Hat Text (body), self-hosted via Fontsource (changed from Space Grotesk and Inter in the redesign, to match the OneText look) | Self-hosting means no requests to Google Fonts, so visitors aren't tracked and the security policy stays strict. | Google Fonts CDN, system fonts | Decided |
| 16 | Website tests | Vitest | Built for Vite, so tests reuse the same config and run in under a second. | Jest (needs extra setup with Vite) | Decided |
| 17 | Page security | Content Security Policy added at build time | The browser refuses any script, style, or connection we didn't list, which blocks most injected code. This matters most in phase 4, when results from scam pages are shown. | No policy (GitHub Pages can't set security headers, so a meta tag is the only option) | Decided |
| 18 | 3D loading | three.js loaded lazily, with an error guard and a frame-rate check | three.js is about 245 kB compressed. Loading it after the page appears keeps the first paint fast. If it fails or runs under 24 frames a second, the page quietly switches to a flat SVG version of the same graph. | Always load 3D; 3D only | Decided |
| 19 | SSRF protection | Our own filtering proxy in the sandbox, plus a guard that checks every resolved IP | Checking a URL once isn't enough: redirects, images, scripts, and DNS answers that change (DNS rebinding) can all reach private addresses later. Forcing every browser connection through a proxy that connects to the exact IP it checked closes all of those at once. | Checking only the first URL; Playwright request interception (can't pin the IP); firewall rules on the host (hard on Docker Desktop) | Decided |
| 20 | Redirect kinds | Chromium's own debugging protocol (CDP) reports why each navigation started | Reading each page's HTML misses instant script redirects, because the page is gone before it can be read. Chromium knows the real reason (meta tag, script, Refresh header, form). HTML reading stays as a backup. | HTML parsing only | Decided |
| 21 | Browser identity | Normal desktop Chrome user agent string, same version | Headless Chrome announces itself as "HeadlessChrome", and many scam kits show a harmless page to anything that does. A normal string is what other URL scanners use. We still never solve or get around CAPTCHAs. | Default headless string | Decided |
| 22 | HTTPS errors in the sandbox | Ignored while visiting | Scam sites often have broken or self-signed certificates. Refusing them would hide the page we're trying to analyze. Phase 3 checks the certificate itself and reports problems. | Refuse bad certificates | Decided |
| 23 | Sandbox tests | Run inside the sandbox image with networking off | Same Chromium as real scans, and the tests provably can't reach the internet (safety rule 9). A tiny local server serves made-up pages; a fake resolver maps test names to addresses. | Tests on the host with a separately installed browser | Decided |
| 24 | Homepage design | Split hero inspired by OneText: content left (60%), live graph right (40%), overlapping dark panel below | Puts the one thing people come to do (paste a link) at the top, and gives the visual its own space instead of sitting behind the text. The graph tells a story in speech bubbles, like OneText's chat bubbles, but with scan data. | Original brief layout (name, cards, then input at the bottom) | Decided |
| 25 | Graph layout | Our own small force simulation (about 150 lines) | Fewer than 50 nodes, so the simple version is fast. It's seeded, so the same scan always gets the same layout, and the same code drives the 3D and the flat fallback. No extra library. | d3-force-3d, react-force-graph (much bigger) | Decided |
| 26 | Domain registration data | RDAP (IANA's bootstrap list picks the right server), with plain WHOIS only for registries that have no RDAP | RDAP is structured JSON and the official successor to WHOIS, so parsing is reliable. Some popular scam TLDs (.io, .co) still lack RDAP, so a small WHOIS fallback covers them. Written in-house (about 150 lines) instead of adding a client library. | python-whois, whoisit | Decided |
| 27 | Server location and owner | MaxMind GeoLite2 City + ASN, read from local files; IP RDAP for the network name and abuse contact | Local lookups are instant, with no per-scan limits, and nothing about a scan is sent to MaxMind. The files refresh weekly (their terms require updates within 30 days). RDAP adds who to report abuse to. | DB-IP Lite (no sign-up, slightly less accurate), online IP APIs (rate limits, send every IP away) | Decided |
| 28 | Certificate history | crt.sh first, Cert Spotter as the backup | crt.sh has the full history (including expired certificates, which shows how long a domain has been around) but is often slow or down; it was down on the day we built this. Cert Spotter is free for personal use and reliable, but lists current certificates only, and the page says so. | crt.sh only; Censys (needs an account) | Decided |
| 29 | DNS lookups | Public resolvers (1.1.1.1, 8.8.8.8) first, then the system resolver; each record type fails on its own | Docker's built-in DNS helper stalled for seconds on some queries (NS for github.com), which sank the whole lookup. Public resolvers answered in milliseconds. Only domain names are sent, same as normal browsing. Override with `DNS_RESOLVERS`. | System resolver only | Decided |
| 30 | TLS certificate capture | In the sandbox, through a separate connection checked by the SSRF guard | Reading the certificate means contacting the site, which only the sandbox may do. Playwright's own security details don't include the names on the certificate, so the sandbox reads the full certificate itself (with the `cryptography` library) and also checks whether a normal browser would trust it. | Playwright security details only (no names, no trust check) | Decided |
